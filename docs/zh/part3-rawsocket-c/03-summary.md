# 4. 总结

* 现在让我们将视角先转回第一部分的内容（我们在这里先不考虑 UDP，因为相对于 TCP 而言 UDP 的结构要简单很多）。回顾我们在 Part 1 中编写的 [tcp_server](../../../01_socket_underlying_c/05_tcp/02_server.c) 和 [tcp_client](../../../01_socket_underlying_c/05_tcp/01_client.c)，在那一整章的内容里，我们只是去聚焦于单个数据包的构建和拆解，却忽略了在 C/S（Client/Server）架构下通信建立的全局视野。就像我们在上一部分利用 Raw Socket 纯手工构建的 SYN 握手数据包，它确实成功经过了检测并发送到了对应的目标路由器或服务器，但是当目标服务器返回一个 SYN-ACK 数据包的时候，却因为我们没有在操作系统的 TCP 状态机里记录这次连接，内核会为了维护协议栈的严谨性，毫不犹豫地向对方发送一个 RST（Reset，重置）包，强制掐断这个莫名其妙的连接。
* 最为戏剧性的一点是，我们利用系统的底层 API 进行越权的单向通信，但是系统本身严格的 TCP 规范却帮我们解决了后续问题。而这也就回到了我们在第一章所着重强调的 C/S 通信模型。在 Part 1 中，那些被我们当做“黑盒”直接调用的标准 Socket API，实际上在底层默默为我们建立了一道极其坚固的契约防线：
  ```text
      [Server]                  [Client]
    socket()                  socket()
        |                         |
      bind()                      |
        |                         |
    listen()                      |
        |                         |
    accept() <---(3-Way)---> connect()
    (Block...)   Handshake        |
        |                         |
      recv() <----(Data)-----   send()
        |                         |
      send()  ----(Data)---->   recv()
        |                         |
    close() <----(4-Way)--->  close()
                Wavehand
  ```


* 在我们调用 `connect` 函数的时候，内核实际上替我们代劳了极为繁重的网络物理操作，它会进行以下几个操作：
* **1. 分配资源：** 在系统内核处创建一个 TCB这相当于在操作系统的档案上正式登记了这次连接的上下文。
* **2. 状态跃迁：** 内核将这个 Socket 的状态从 CLOSED 修改为 SYN_SENT。
* **3. 代为发包：** 内核自动帮你构造一个 SYN 包并发送出去（这正是我们在 Part 3 中用 Raw Socket 纯手工拼接的那个二进制阵列）。
* **4. 启动定时器：** 内核开始计时，并挂起你的程序，默默等待对方回复 SYN-ACK。


* 相应的，`accept` 和 `listen` 则是将服务器的端口 80 变成 LISTEN 状态。我们在 Part 1 中只是简单调用了它们，但此刻站在底层的视角，这两个函数的真实机理如下：
* **`listen()` =** 当服务端调用 `listen()` 时，内核并不会向网络中发送任何数据包。它是在系统的内核空间中为这个 Socket 开辟了两个至关重要的结构：半连接队列（SYN Queue） 和 全连接队列（Accept Queue）。它向网卡和底层协议栈宣告：任何目标端口为 80 的 SYN 握手请求，都由起来接管。
* **`accept()`** `accept()` 实际上是一个完全脱离了网络发包逻辑的纯内存操作。当客户端的 SYN 到达，内核自动回复 SYN-ACK，连接进入半连接队列；当客户端最后的 ACK 到达，三次握手在内核态悄无声息地完成，这个成熟的连接（TCB）就被移入全连接队列。而 `accept()` 的唯一作用，就是阻塞当前线程，死死盯住全连接队列。一旦队列里有了完成握手的连接，它就把这个连接“摘”出来，包装成一个新的 Socket 文件描述符（fd）丢给应用层。

* 结合这种状态机的严密逻辑，这里你可以清晰地看到的是，在使用 Raw Socket 盲发 SYN 的场景下，当目标机器的 tcp_acp（即 SYN-ACK 回包）数据包返回的时候，就会因为在我们自己的内核里并没有对应的 pcb（没有调用过 connect 登记记录），因此内核会直接判定这是一个非法的幽灵数据包，随即发送 RST 来掐断 TCP 连接。
* 现在，我们终于能透过一窥 C 语言函数调用的底层细节，并清楚地看到这些细节是如何和操作系统内核深度交互来实现网络通信协议的。在这个角度上，数据包的物理传输和发送，仅仅只是支撑起宏大 C/S 架构的一块基石而已。
* 但这远不至于仅仅停留在 C/S 架构。经历了 Part 1 的黑盒调用、Part 2 的并发模型，再到本章 Part 3 的降维解剖，当我们再去思考网络数据包的流转的时候，**不应再局限于仅仅关注繁琐的字段细节**。尽管为了展现协议在数据包层级的具体实现，我们极其详细地对结构体对齐、字节序和校验和进行了硬核的讨论，但我们真正的目的，是将视角重新拉高，转向现实生产中复杂的网络交互架构，并深刻理解那些冰冷的协议规范，究竟是如何为了实现、符合这些上层架构中特定功能点位（如安全防御、连接复用、状态同步）而做出的字段设计妥协。
* **我们去关注细节，绝不是为了在细节上纠缠与死磕，而是为了在抽丝剥茧之后，能够在更宏观的视角中精准把握到技术演进的脉络。** 只有当亲手拼接过二进制的协议头，当真切体会过机器物理逻辑与人类抽象逻辑的剧烈冲突后，我们才终于可以理解，一个简单的`http.Get`后包含逐层递进，接口封装的计算机结构。
