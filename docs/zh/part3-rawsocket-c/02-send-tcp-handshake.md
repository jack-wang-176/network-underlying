# 3. TCP 握手包的发送

* 在之前的数据包拆解部分，我们只需要对一个已经接收到的完整数据包进行指针偏移，并套上对应的协议结构体外壳即可读取数据。而在本节的发送部分，我们则需要深入探讨之前被忽略的技术细节，亲自动手从零组装一个数据包，去真实感受计算机协议栈是如何在底层保证数据发送的正确性与严谨性的。
* 首先，让我们把目光投向协议结构体的内存布局。以数据链路层的 `ethhdr` 为例，如果你尝试在代码中手写这个结构体：
  ```c
    struct my_ethhdr {
      unsigned char  h_dest[6];
      unsigned char  h_source[6];
      unsigned short h_proto;
  };
  ```


* 按照字面计算，你会理所当然地认为这个结构体的大小是 $6 + 6 + 2 = 14$ 个字节。但是，如果你尝试用 `sizeof()` 配合 `printf` 进行打印，却可能会发现编译器告诉你它是 16 个字节！这是因为当 CPU 通过内存总线进行寻址时，为了提高读取效率，它更习惯于以 4 字节或 8 字节对齐的方式进行数据吞吐。因此，编译器会在编译阶段擅自做主，在结构体的末尾（或中间）加上两个字节的空白填充（Padding）。 这也就是为什么在 `<linux/if_ether.h>` 等系统头文件封装网络协议结构体时，末尾必定会带有一个 `__attribute__((packed))`。只有添加了这个编译器修饰符，我们才能强行关闭字节对齐优化，在真正意义上用 C 语言的结构体严丝合缝地映射出网络线缆中传输的连续物理内存。
* 第二个关键细节是**校验和（Checksum）**。这个字段主要用于检验数据包在物理传输过程中是否发生了内容损坏。在编写高级语言时，我们往往理所当然地相信数据传输是绝对可靠的；但在真实的物理网络中，电信号会衰减，射线可能会导致内存中的比特位发生翻转，路由器也可能因为内部拥塞或硬件故障破坏数据包。面对如此不可控的物理网络，内核的解决方案是：**不相信任何未经数学自证的数据**。TCP/IP 协议栈正是通过“16位反码求和”的校验机制来保障逻辑连接的可靠性。在发送数据包时，发送方必须预先计算并填入校验和；在接收方解析时，内核会提取报文重新计算并比对，一旦不匹配则直接丢弃。
  ```c
    unsigned short checksum(void* b,int len){
      unsigned short *buf = b;
      unsigned int sum = 0;
      unsigned short result;
      for(sum = 0; len >1 ; len-=2){
        sum += *buf++;
      }
      if (len == 1){
        sum += *(unsigned char*)buf;
      }
      sum = (sum >> 16)+(sum & 0xFFFF);
      sum +=(sum >> 16);
      result = ~sum;
      return result;
    }
  ```
* 在 IP 协议中，校验和仅仅针对**协议头部**进行计算。我们首先要明白这段经典代码的核心算法思想：把连续的内存数据当成一堆 16 位（2 字节）的数字，将它们全部累加起来；如果加法过程中产生了溢出（进位），就把进位加回到最低位；最后对总和按位取反。这种设计思路主要妥协于互联网诞生之初 CPU 极其有限的算力：加法指令执行速度极快，最后的结果也能精简地塞进一个 2 字节的空间中，并且这套算法拥有优秀的数学特性——无论是大端存储还是小端存储的机器，校验逻辑都能完美兼容。
* 需要特别指出的是，网络中的数据校验并非全由网络层一方承担。这是一个分层协作的过程：底层的**数据链路层**通过 CRC/FCS 算法实现严格的比特位级别纠错；最顶层的**应用层**则通过 TLS/SSL 证书等密码学手段防范人为的安全篡改。夹在中间的 IP/TCP 层，其网络校验的核心原则就是：**用最少的 CPU 时钟周期，换取“足够用”的错误拦截率**。
* 让我们深入剖析一下这段看似简陋、实则极为巧妙的 C 语言代码。这里使用 `unsigned short` 指针将内存按两字节进行切分步进，同时使用 `unsigned int` (32位) 来存储加法结果，其精髓在于**将溢出后的进位数据也完好地暂存起来**。由于最终返回的校验和字段必须是 16 位，所以函数返回值依旧使用 `unsigned short`。
* 代码在通过 `for` 循环切分并直接相加后，紧接着的 `sum = (sum >> 16) + (sum & 0xFFFF);` 是点睛之笔：`(sum >> 16)` 提取了溢出到高 16 位的进位数据，`(sum & 0xFFFF)` 则将低 16 位的有效结果剥离出来，两者相加实现了“进位回卷”。随后的 `sum += (sum >> 16);` 则是为了处理上一步相加过程中可能触发的极罕见的二次溢出问题。最后通过 `result = ~sum;` 完成按位取反，大功告成。
* 到此为止，我们已经成功理清了 IP 头部涉及的校验和计算。但是，当你着手准备计算 **TCP 字段的校验和**时，情况又变得有些棘手。TCP 协议规范强制要求我们在计算校验和时，必须把 IP 头部的一部分关键信息（如源 IP 和目标 IP）也纳入计算范围内。当你熟悉了协议从上到下的组装流程后就会发现一个时间差矛盾：**在构建 TCP 头部的时候，底层的 IP 头部明明还没有被附加到数据包上！**
* 为什么 TCP 协议非要这么设计呢？正如我们之前所讨论的，IP 头部中有一个 TTL 字段，数据包每经历一次路由器跳转，TTL 就会被自动减一，随后路由器会重新计算 IP 校验和。如果在极少数情况下，路由器的硬件故障导致了 IP 头部中的“目的 IP 地址”发生了位翻转，而恰好重新计算出的 IP 校验和也通过了，这个数据包就会被错误地投递给无关的主机。为了防止这种“南辕北辙”的致命错误，TCP 决定给自己上个双保险：它强行把 IP 地址拉入自己的校验计算中。这样，即使底层 IP 地址被中途意外篡改，到达终点后 TCP 的校验和也绝对无法匹配，从而避免接收错误的数据。
* 为了解决“尚未封装完整的 IP 包，却要使用 IP 地址进行校验”的越权计算问题，我们必须在代码内部定义出一个**在实际网络线缆中并不存在、仅仅在主机内存计算时充当临时模具的“伪首部”**：
  ```c
    // 伪首部：传输层跨越网络层的一份额外交保
  struct pseudo_header {
      unsigned int source_address; // 源 IP 地址 (4 字节)
      unsigned int dest_address;   // 目的 IP 地址 (4 字节)
      unsigned char placeholder;   // 必须填 0 (1 字节)
      unsigned char protocol;      // 协议号，TCP 是 6 (1 字节)
      unsigned short tcp_length;   // TCP 头部长度 + Payload 长度 (2 字节)
  } __attribute__((packed));       // 呼应上述部分：绝不允许编译器在这里塞入哪怕一个字节的 Padding！
  ```
* 需要特别注意的是 `placeholder` 这个占位符字段。如果没有这个字段，整个伪首部的长度就是 11 个字节的奇数。为了符合现代 CPU 以 4 字节（或 8 字节）偶数边界为单位处理数据的底层习惯，并方便后续 16 位的校验和累加，协议设计者刻意在这里填入了一个 `0` 凑足 12 字节。
* 在配套代码 [send_syn_package](../../../03_rawsocket_underlying_c/03_Send_Package_Of_Tcp/sendtcp.c) 中，我们详细展示了如何使用 `raw_socket` 从零组装并发送一个 TCP SYN 握手数据包。有趣的是，你可以直接同时运行我们在本章第二部分编写的 [parse_tcp](../../../03_rawsocket_underlying_c/02_Pointer_Casting%26%26Decapsulation/04_parse_TCP.c) 数据包分析程序，来实时监测你刚刚发出的这个包。当然，你需要根据自己所处的网络环境，将代码中宏定义或开头的全局变量替换为你本机的实际 MAC 地址和 IP 地址。如果你在 WSL 或是 Linux 环境下，也可以使用如下命令开启系统自带的极客抓包工具进行监测：
  ```bash
    sudo tcpdump -i eth0 -n -vvv -X dst host <your_target_ip> and tcp port 80
  ```
* 回顾发送代码的逻辑流程：我们首先在栈中申请了一片连续的字节数组作为缓冲内存，随后利用相应的结构体指针（`ethhdr`, `iphdr`, `tcphdr` 等）对这片数组的头部进行网格化的划分与封装（由于我们预先知道了握手包的总体积，这块内存的申请可以相对随意）。接下来的工作就是像填表一样对各个字段进行赋值，细节在此不再赘述。真正值得警惕的是：**任何大于单字节的数据结构，在填入前必须通过 `htons()` / `htonl()` 转换为网络大端字节序**；而点分十进制的 IP 字符串，则需通过 `inet_addr()` 翻译为 32 位无符号整数。为了照顾较少接触底层语言的读者，下面我们简要梳理一下在这些代码中频繁出场的 C 语言内存处理利器。
* 在开始前我们需要明确一个共识：在 C 语言的底层视角中，各种高级的数据结构和数组，本质上不过是一块物理连续的内存而已，字符串则依靠 `\0` 来标识数据的终点。在此基础上，你就能看透代码中数组、指针与内存操作之间的转换本质：
* **`memcpy`**：无视类型，直接将特定大小的内存块整体克隆。我们在拼接伪首部和计算校验和时，通过指定明确的字节大小，精准地控制了数据的拷贝边界，防止内存溢出。
* **`strcpy` 与 `strncpy`**：专为字符串拷贝而生。`strcpy` 在底层利用纯粹的指针位移，将字符一一填入目标地址，直至撞见 `\0` 才肯罢休。区别于 `memcpy` 的固定长度拷贝，`strncpy` 增加了最大长度的限制门槛以防止溢出。在这里必须厘清一个极易混淆的底层认知错觉。在写代码时，我们往往能心安理得地 **“把指针直接等同于一个安全的连续内存数组来操作”**，这在很大程度上是栈内存（Stack）赋予我们的一种“特权”幻觉。当你在栈上声明 `char buf[1024]` 时，编译器在分配阶段就清晰地掌握了这块领地的物理边界，数组名作为整体代表着一段确定的空间，只是在传参时才退化为指针。然而，一旦脱离了栈的温室——比如面对一个纯粹的裸指针，或者在堆内存（Heap）中通过 `malloc` 划分出的空间——你必须时刻警醒：**指针仅仅是一个指向起点的路标，它身上绝对不携带任何关于“容量上限”的信息**。如果失去了栈数组那种天然的边界感，依然带着“它是一个安全数组”的惯性思维去盲目调用 `strcpy` 进行写入(或者仅仅只是对裸指针`strcpy`进行写入数据)，就极有可能跨过那道看不见的边界，引发灾难性的内存覆盖（Memory Corruption）
* **`strlen`**：初学者往往误以为它是用来“测量数组物理大小”的工具，这并不准确。`strlen` 唯一的逻辑是从你给定的指针地址出发，向后逐字节排查，直到撞见第一个 `\0` 为止，并返回走过的步数。因此，在使用 `strcpy` 写入一段文本后，再次向 `strlen` 传入首地址，就能精准测量出我们刚刚写入的动态载荷长度。

* 掌握了这些，你就能透彻理解这段发送代码中惊心动魄的内存操控艺术：C 语言是如何允许我们在最底层直接掌控物理内存，通过纯粹的指针偏移与协议模具的嵌套，在规范要求的绝对坐标上完成数据写入；同时又极其优雅地调用主机网络字节序转换函数，弭平了庞大的异构互联网中“大端机器”与“小端机器”的硬件鸿沟。

* 至此，我们利用 Raw Socket 成功地逆向完成了整个协议栈的拼图，从零手搓并发送了一个合法的 TCP SYN 握手数据包。在这个过程中，我们穿越了高级网络库的封装幻象，亲历了处理结构体内存对齐的陷阱、手算了 IP 与 TCP 的双重校验和、并利用伪首部解决了跨层验证的难题。
掌握了这项直接“在网线上涂鸦”的底层能力后，你的视野绝不再局限于发送一个简单的握手包——只要你能遵守对应协议的内存排布法则，你可以随意修改代码中的控制标志位（Flags）与载荷（Payload），去自由地构造 RST 攻击包、伪造源 IP 数据报、甚至自己去实现一套专属于你的自定义网络协议。
